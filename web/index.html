What is real? Kubernetes, YAML, and the shell. This foundation lesson creates a namespace and a ConfigMap. DPF, Kamaji, tenant control planes, and simulated DPUs are later lessons. A namespace alone is not a DPF tenant cluster.

1

Meet your cluster

A node runs Kubernetes components or workloads. This lab has one control-plane node and one worker, both running as Docker containers.

kubectl get nodes

Expect two nodes with status Ready.

2

Read the prepared YAML

The simulator includes the complete manifest. A namespace groups resources. A ConfigMap stores non-secret settings. The file describes both, separated by ---.

cat /app/lessons/europe.yaml

The Europe settings are already filled in. No editing is needed.

Explain the fields

apiVersion and kind identify the resource type. metadata.name names it. The label identifies Europe. metadata.namespace places the ConfigMap inside Europe, and data holds its settings.

3

Apply and inspect

apply asks Kubernetes to make the cluster match the bundled YAML. Applying the same file again reconciles the desired settings.

kubectl apply -f /app/lessons/europe.yaml
kubectl get configmap lab-identity -n tenant-europe -o yaml

Expect region: europe and environment: simulation.

4

Check your work

The checker reads the live namespace, its label, and the ConfigMap. It does not apply the solution for you.

Ready when you are.
Need a hint?

If a check fails, apply the bundled file from step 3 again, then check. The expected values are already provided; no file editing is needed.

Reset deletes tenant-europe and everything inside it and restores the prepared workspace YAML. Other training namespaces are kept.
