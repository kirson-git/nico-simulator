    BF4: what changes during installation?
    

    Goal: distinguish the DPU OS, firmware and service containers, then choose the installation path for the correct generation. The console above remains a BF3 rehearsal; this section explains BF4 differences.
    

    

    BF3 exercise above
    1. Host with BFB + bf.cfg
    2. RShim transfer to the DPU
    3. Arm OS boots; configure HBN separately
    

    BF4 DPU mode · DMS 3.5
    1. Controller with ISO / PLDM
    2. DPU BMC manages installation
    3. Verify OS and activated firmware, then services
    

    

    The BF4 path shown here follows DOCA 3.5 DMS provisioning, section 7. DMS is the management tool; DPF is the Kubernetes orchestration framework.
    

    QuestionBF3 exerciseBF4 DPU mode in DMS 3.5
    

    Installation files?BFB bundle and prepared bf.cfg.ISO for the OS; PLDM for firmware; a combined operation is supported.
    

    Who installs?The host pushes through RShim.The controller contacts the DPU BMC. The BMC handles media and boot.
    

    Network requirement?This exercise models a local RShim transfer.Controller → BMC; BMC → ISO source. Test both paths.
    

    When is firmware active?Follow the selected bundle’s reset requirements.Full card power cycle after PLDM completes; an Arm reset is insufficient.

    NIC mode is different: DMS 3.5 describes a local PLDM firmware update through MFT/MST, without the DPU BMC. That is not an Arm OS installation.
    

    Keep the two computers separate. The BlueField OS ISO targets the DPU’s Arm computer. It does not install Ubuntu on the x86 server. HBN is another layer: booting an OS does not prove that HBN is running or forwarding traffic.
    

    What changes when NICo uses DPF?
    

    In the documented NICo/DPF integration, BF3 selects bfb_url. BF4 instead selects bluefield_software: an OS ISO plus a non-empty map from PSID (Parameter Set ID) to firmware bundle URL. Do not set both selectors.
    

    Inspect the prepared BF4 configuration excerpt

    TOML, not Kubernetes YAML. This is a partial NICo configuration example with fictional URLs and PSID. It is for reading only; no file editing or deployment is part of this lesson.
    

    [dpf.deployments.bf4_generic]
flavor_name = "training-bf4-flavor"
deployment_name = "training-bf4"
node_label_key = "training.example.com/bf4"

[dpf.deployments.bf4_generic.bluefield_software]
os_iso = "https://images.example.com/bf4-os.iso"

[dpf.deployments.bf4_generic.bluefield_software.pldm_fw_bundle]
"EXAMPLE_PSID" = "https://images.example.com/bf4-firmware.pldm"
    

    NICo consumes these settings and orchestrates DPF resources; the DPU does not read this TOML file. Each deployment needs distinct deployment, flavor and node-label identifiers. PSID selects the matching firmware, not a tenant.
    

    

    Generic BF4 and BF4 Astra differ: generic BF4 uses DPUFlavor; Astra uses DPUFlavorTemplate and requires the documented Spectrum-X runtime ConfigMap before activation. Choose the appropriate deployment profile.
    

    What carries over from the terminal exercise?
    

    Keep the habit of checking identity, installation completion, service health, forwarding and independent management separately. Revalidate device paths, mode/reset commands, manifests and host restrictions for BF4; the BF3 command list is not a BF4 recipe.
    

    The HBN 3.4 validated platform list names BF2/BF3. That list does not validate this lesson’s standalone HBN commands for BF4. Select the HBN release and deployment guide for your BF4 platform.

    DPU recap, goal and animated flow

    What is a DPU? A network adapter with its own Arm computer, memory, operating system and networking hardware. The server runs its host OS; the DPU runs a separate Arm OS. A BMC provides a separate management path.
    

    Your goal
    Understand each manual step before learning how DPF automates it. Identify where a command runs and what it changes.
    Your outcome
    A simulated DPU with a verified BFB-installed OS, checked HBN services, a tested sample route, restricted host access and working independent management.
    

    

    Order matters: DPU mode → BFB and Arm OS → HBN container → forwarding checks → host restrictions. HBN is itself a containerized service. A BFB installation alone does not make HBN operational.
