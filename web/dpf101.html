Why do we need DPF?

A DPU is a computer you must operate. Now imagine operating hundreds of them.

For one DPU, you can install its OS, configure ports, start HBN and check the results manually. Repeat that for every server, then repeat it again when software changes. Keeping versions and settings consistent becomes an operations problem.

The motivation: turn a repeated device-by-device procedure into a declared, repeatable fleet workflow—with status you can inspect.

What is DPF?

DOCA Platform Framework uses Kubernetes APIs to provision supported BlueField DPUs and manage their services. You describe the desired deployment; controllers compare it with the observed state and work to make them agree. This ongoing loop is called reconciliation.

DPF coordinates the work. The DPU provides the hardware; its OS runs the software; a service such as HBN provides networking functions. NVIDIA DPF overview ↗

Where would we use it?

A growing DPU fleet

Example: provision the same approved software and configuration across a rack, then see which DPUs need attention.

Infrastructure services

Deploy and manage networking, storage or telemetry services on DPUs. For our course, HBN is the networking example.

Separately managed hosts

In a Zero Trust design, infrastructure administrators manage DPUs separately from workload hosts. DPF supports that deployment model.

When might you skip it? For a small manual experiment or basic NIC operation, a full DPF environment may add more work than it saves. This is a design tradeoff, not a minimum device-count rule. DPF becomes useful when repeatability and ongoing operations matter.

Zero Trust also requires the appropriate management network, host restrictions and service configuration. Installing an operator or naming tenants “Europe” and “Asia” does not create isolation. NVIDIA Zero Trust architecture ↗

Where does DPF fit?

What work does it coordinate?

  1. Identify and provision. Select the DPUs and compatible installation artifacts; configure the DPU system.
  2. Deploy services. Run the chosen services and configure their network connections.
  3. Observe and reconcile. Inspect status, address failed prerequisites and manage lifecycle changes through the declared configuration.

An operator being installed is only the starting point. A DPU OS booting, a service running and traffic forwarding correctly are separate outcomes to verify. DPF cannot repair missing cabling or make an unsupported software combination compatible.

Meet the names you will see in later lessons
DPF operator
Manages the DPF system components in Kubernetes.
DPU cluster
A Kubernetes environment whose worker nodes are DPUs. Its control plane and the management cluster are distinct roles.
DPUFlavor / DPUSet
Describe system settings and manage DPU provisioning.
DPUService / DPUServiceChain
Describe services and how traffic is steered between their interfaces.

No YAML is needed yet. These terms are introduced in the DPF architecture and resource reference.

Your takeaway: choose DPF when you want a repeatable way to provision and operate DPU infrastructure through Kubernetes. It manages the lifecycle; the DPU and its services do the work.
