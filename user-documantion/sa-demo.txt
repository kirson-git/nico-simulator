DPF SA PRESENTATION

Open http://localhost:8780/sa-demo after starting the course.
Eleven linked scenes explain why DPF exists, the DPU/DOCA/DPF layers, service
examples, an NVL72 rack, fleet YAML, tenant isolation, rollout, service behavior,
lifecycle changes and new-service integration.

CONTROLS
Use the scene list, Previous/Next or the left/right keyboard arrows.
Arrow keys inside diagrams scroll the picture instead of changing scenes.
Presentation mode hides the sidebar; Escape restores it. It does not request
browser full-screen access. Speaker notes can be shown separately.
Animation controls are on the upper right: Play/Pause, Step and Replay.
Animations start paused, stop when changing scenes or hiding the tab, and use
single-step playback when reduced motion is enabled in the operating system.
Each scene has a linkable URL fragment, such as /sa-demo#rollout.

CONTENT BOUNDARY
All motion, fleet devices and examples are authored illustrations. No live
installation, health measurement, attack detection or packet transfer occurs.
The service examples are HBN, Argus, SNAP and DOCA Telemetry, grounded in the
linked NVIDIA DPF 26.4.0 guides. They are not a validated combined deployment or
a BF4 compatibility promise. DOCA is the software ecosystem, not a single peer
container. The course owner's TOWER and HBA labels await clarification.

Reused original board imagery remains unchanged. The new SVG diagrams reuse the
course animation controller and separate management, forwarding and inspection.
Argus inspects host memory and emits events; it is not shown as an inline firewall.

A smaller initial deployment set is an operator practice, not a claim that DPF
provides automatic canary analysis. Update disruption depends on configuration.
New services require compatible images, conformant charts and validation.

NVL72 / FLEET / TENANTS
Direct links: /sa-demo#rack, /sa-demo#fleet, /sa-demo#selection, /sa-demo#tenants.
The hardware example is GB300 NVL72 AI Factory reference design: 18 compute trays, 72 GPUs, 36 CPUs,
and 18 BlueField-3 DPUs (one per tray). Other NVL72 designs have different DPU
counts. This is a conceptual DPF overlay, not proof of a validated DGX deployment.

The #selection telemetry demonstration selects two east racks in one DPF management domain;
a west rack is excluded. Select Baseline or Detailed telemetry, open the full
YAML, then use Play or Step. Only spec.services.dts.serviceConfiguration changes.
No API requests or live installations are made. Two racks x 18 DPUs = 36 example
targets; this is not a supported scale limit or measured rollout result.

Prepared dependency names and demo.example.com labels are fictional. Inventory,
DPU clusters, credentials, BFB, flavor, service template and both profiles must
already exist. BFB/flavor/template/profile references share the deployment's
namespace. Both profiles and template must use deploymentServiceName: dts.
The complete illustrative object is saved in examples/sa-demo/ below this folder.
These files are not an installation bundle. The browser has the same prepared
example; users do not need to edit it. API fields were checked against NVIDIA's
v26.4.0 Go definitions for DPUDeployment and DPUSet.

nodeEffect.hold: true waits for external maintenance coordination when node
effect is applied. RollingUpdate controls DPUSet changes; service upgrade policy
also determines disruption. Neither means automatic zero downtime or rollback.
Independent DPF management domains require an additional delivery workflow.

The separate Europe/Asia scenario reserves whole racks per tenant: 01-02 for
Europe, 03-04 for Asia. HBN VRFs, interface assignments, VXLAN VNIs and matching
EVPN policy provide the illustrated network separation. Same-tenant connectivity
must pass, cross-tenant access must fail without explicit permission. Management
identity/RBAC and host restrictions, GPU scheduling, storage permissions and
compute-fabric isolation are separate controls. DPF deploys desired configuration;
HBN/fabric policy enforce the data path. Kamaji tenant clusters and namespaces
alone do not establish these customer boundaries. VXLAN is not encryption.

KUBERNETES-TO-DPU LIFECYCLE
/sa-demo#fleet shows a three-node management Kubernetes cluster on the left,
a separate server host OS and BlueField-3 DPU on the right. DPF's Zero Trust
provisioning goes through BMC/Redfish. The compatible full BFB provides the Arm
OS/firmware/DOCA baseline; Arm Linux joins the DPU Kubernetes cluster, whose
control plane is hosted by Kamaji in this example. Argo CD synchronizes the
service workloads; DPU runtime image pulls and container execution are separate
from BFB installation. No service compatibility or production readiness is
implied by the animation. HBN, Argus and telemetry each need configuration.
Tower remains unverified until the product/reference is clarified.

The left component grouping is logical scheduling across three management
nodes, not fixed pod placement, mandatory replica counts or a complete HA design.
Required prerequisites, replaceable default cluster/storage providers and
optional monitoring are distinguished in the expanded prerequisite table.
Production validation includes isolation, certificates, access, service tests,
capacity, observability, recovery and upgrades. Green pods alone are insufficient.
